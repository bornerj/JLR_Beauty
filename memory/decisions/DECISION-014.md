Status: ACTIVE
Date: 2026-08-16
Context: `DECISION-013` regra #5 estabeleceu que Cadastros (Produtos/Serviços/Planos/Pessoas/Cupons/Entrega) e telas de Sistema (Branding/Textos/Seções/Integrações/Segurança/Infra) não seriam reescritas esteticamente "até haver valor real comprovado em uma versão nativa" — o `PLAN-0024` (RETROFIT-020/021) entregou essas áreas como hubs de adapter/link pro Admin legado, exatamente dentro dessa regra. O usuário pediu agora ("faça o PLAN-0026") a reescrita nativa dessas telas dentro do Admin V2, e autorizou explicitamente a alteração desta regra "hoje, nesse caso específico". Antes de decidir, foi feito RAG nos 3 sistemas de conteúdo endereçável por banco (Textos das Páginas, Seções Telas, Galeria de Mídias — todos guardados como blobs JSON na tabela genérica `Setting`/`ContentEntry`, com catálogo de campos definido em TypeScript, não no schema) e no restante das telas de Cadastro/Sistema (contagem de linhas por módulo como proxy de complexidade real). Achado decisivo: várias telas do legado (`admin-people` 2.708 linhas, `admin-products` 1.436, `admin-services` 679, `admin-whatsapp-contacts` 470, `admin-tests` 453) são construídas num padrão imperativo antigo (`behavior.ts` com `querySelector`/`addEventListener` manual sobre HTML estático), diferente do resto do projeto inteiro (site público e 100% do Admin V2 são React declarativo) — "nativizar" essas telas não é um reskin, é reescrever a camada de interação do zero. Já as telas de config/settings-form (Cupons, Entrega, Planos, Branding) e os 3 sistemas de conteúdo endereçável (Textos, Seções, Galeria) já são React puro e consomem endpoints que já existem — confirmado que **100% do backend CRUD necessário já existe** (`catalog.ts` para Produtos/Serviços, `users.ts`, `schedule.ts` para Pessoas/Profissionais/Clientes, `subscriptions.ts` para Planos, `admin.ts` para Cupons/Textos/Seções/Galeria/Branding/Entrega) — nenhum endpoint novo é necessário para este plano, só frontend novo.
Decision: A regra #5 da `DECISION-013` é **substituída** por: Cadastros e Sistema passam a ser reescritos nativamente dentro do Admin V2 (`apps/web/src/admin-v2/`), planejados e executados via `PLAN-0026`. Regras fixadas para essa reescrita:
1. **Componentes novos, nunca edição in-place**: cada tela nativa é um módulo novo dentro de `apps/web/src/admin-v2/`, seguindo o mesmo padrão já estabelecido (`types.ts` + `service.ts` quando necessário no backend + `View.tsx` + `components/` no frontend). Os módulos legados (`apps/web/src/modules/admin-*/`) permanecem intocados, servindo `/admin` normalmente — nenhuma dependência de código entre V2 e legado além de rotas/endpoints de API já existentes e compartilhados.
2. **Reuso obrigatório de backend**: nenhuma rota de API nova é criada por padrão para CRUD que já existe (`catalog.ts`, `users.ts`, `schedule.ts`, `subscriptions.ts`, `admin.ts`) — o Admin V2 nativo consome os mesmos endpoints que o legado já usa. Gap real de backend encontrado durante uma onda (ex.: paginação/filtro server-side ausente) é aditivo, nunca reescreve a regra de negócio existente.
3. **Modularidade explícita**: telas legadas que hoje agregam múltiplas entidades num só componente monolítico (ex.: "Pessoas" = Clientes + Profissionais + Usuários numa tela só com abas) são **desmembradas** em telas nativas independentes, uma por entidade, cada uma sua própria rota/onda — nunca replicar um mega-componente no V2.
4. **Sequenciamento por complexidade real, não por ordem alfabética**: prioridade é dada às telas mais próximas de um "reskin" (React puro, sem `behavior.ts` imperativo) primeiro; as duas telas mais pesadas (Produtos, Pessoas — por causa de estoque multi-unidade e sub-perfis de profissional) ficam por último, cada uma isolada na sua própria onda.
5. **Identidade visual**: segue as regras #6 (paleta) e #4 (cálculo de negócio só no backend) da `DECISION-013`, sem exceção — não revalidadas onda a onda.
6. **Aposentadoria do legado continua fora de escopo**: a existência de uma versão nativa de uma tela **não** implica remover a tela legada equivalente automaticamente — a regra #3 da `DECISION-013` (aposentadoria não decidida) continua valendo até nova decisão explícita (RETROFIT-022, ainda sem critério fixado).
Consequences: `DECISION-013` regra #5 fica marcada como substituída por esta decisão (ver nota na própria `DECISION-013`). Todas as ondas do `PLAN-0026` herdam as 6 regras acima sem revalidação onda a onda. Qualquer proposta futura de reescrever uma tela editando o módulo legado em vez de criar um componente novo, ou de criar um endpoint de API duplicado quando um já existe, deve primeiro atualizar esta decisão.
