Status: ACTIVE
Date: 2026-08-17
Context: `PLAN-0022` (Onda 9 + RETROFIT-010b) tinha fixado, como padrão de interação dos kanban do Admin V2, "usuário nunca arrasta — mesma linguagem do Mapa da Rede" — movimentação de estado sempre via controle explícito (`<select>` no card), nunca drag-and-drop. O usuário pediu agora (2026-08-17) drag-and-drop no Board Operacional de Pedidos (`Operação`) e no Pipeline de Franquias (`Crescimento`), pensado como rotina reusável pros kanban do Admin V2. RAG antes de decidir: os dois boards têm mecanismos de dado diferentes — Pedidos tem colunas **calculadas** a cada load (`status`+`fulfillmentStatus`+um alerta de tempo, `operational-orders/service.ts`), não um campo salvo; Franquias tem `stage`, um campo real, com endpoint de escrita já existente e motivo obrigatório desde `PLAN-0025`. Perguntado ao usuário antes de codar: (1) comportamento da coluna "Atenção" em Pedidos (não é uma etapa real, é alerta); (2) qual `fulfillmentStatus` gravar ao soltar em "Prontos" (3 valores reais colapsados numa coluna só); (3) confirmação explícita pra reverter a regra "nunca arrasta" em Franquias. Biblioteca escolhida: `dnd-kit` (`react-beautiful-dnd` está arquivada e tem incompatibilidades conhecidas com React 19; API nativa HTML5 exigiria reconstruir acessibilidade/touch do zero) — dependência nova aprovada explicitamente pelo usuário antes da instalação.
Decision: A regra "usuário nunca arrasta" de `PLAN-0022`/RETROFIT-010b é **substituída** por: drag-and-drop é o padrão de interação padrão dos kanban do Admin V2 daqui pra frente, implementado via uma primitiva reusável (`apps/web/src/admin-v2/shell/kanban/KanbanDndBoard.tsx`, `PLAN-0029`). Regras fixadas:
1. **Coluna arrastável é decisão por board, não automática**: cada coluna declara explicitamente se aceita ser origem/destino de drag (`draggable`/`droppable` boolean). Colunas que representam um *alerta* ou um *estado automático* (não uma escolha manual do usuário) ficam sempre fixas — ex.: "Atenção" e "Entraram" no Board de Pedidos (nem recebem nem soltam card por drag). Nenhum board assume por padrão que toda coluna é arrastável.
2. **Coluna calculada exige um mapeamento explícito e documentado pra cada destino arrastável**: quando a coluna do board não é 1:1 com um campo salvo (caso de Pedidos, que colapsa múltiplos valores reais de `fulfillmentStatus` por coluna), o valor gravado ao soltar em cada coluna precisa estar documentado no componente (`FULFILLMENT_STATUS_BY_COLUMN`, `OrdersBoardView.tsx`) e ter sido decidido explicitamente com o usuário — nunca inferido/adivinhado pela IA.
3. **Mudança que já exigia confirmação/motivo continua exigindo**: trocar o gatilho de "select" pra "drag" não remove nenhuma validação de negócio existente — o Pipeline de Franquias continua abrindo o modal de motivo obrigatório (`StageChangeReasonModal`) antes de qualquer escrita real; soltar o card só sinaliza a intenção, nunca commita direto.
4. **Reuso de endpoint obrigatório**: nenhum endpoint novo de escrita é criado pra suportar drag — Pedidos reusa `PATCH /orders/:id/fulfillment` (legado, já validava pagamento aprovado antes de progredir fulfillment); Franquias reusa `PATCH /admin-v2/growth/franchises/:id/stage` (RETROFIT-010b, inalterado).
5. **Biblioteca fixa do projeto pra drag-and-drop**: `@dnd-kit/core` — não introduzir `react-beautiful-dnd` (arquivada) nem reimplementar via HTML5 DnD API nativa em nenhum kanban futuro; usar/estender `KanbanDndBoard.tsx`.
Consequences: `PLAN-0022`/RETROFIT-010b fica marcado como parcialmente substituído por esta decisão (a parte de interação — o resto do RETROFIT-010b, movimento livre entre qualquer etapa e a regra de negócio de `moveLeadStage`, continua valendo sem mudança). Qualquer kanban futuro do Admin V2 (ex.: se o Mapa da Rede ganhar uma ação de mover unidade entre grupos) deve reusar `KanbanDndBoard.tsx` em vez de implementar drag-and-drop do zero, e deve passar pela mesma checklist de decisão (quais colunas são arrastáveis, qual valor cada destino grava) antes de codar.
