Status: ACTIVE
Date: 2026-08-20
Context: Levantamento de fechamento do `PLAN-0032` (ocorrência #6) mapeou as 15 telas do menu do Admin legado contra o Admin V2 — 12/15 já tinham equivalente nativo (`PLAN-0022`/`0023`/`0026`/`0031`), e as 3 restantes (Metas, Performance, Assinantes) nunca tiveram implementação real por trás (zero chamada de API, zero model no schema — conteúdo de template estático). RAG adicional confirmou zero acoplamento de código entre Admin V2 e os módulos legados (`modules/admin-*`): nenhuma tela nativa importa nada de lá, e o backend compartilhado (`routes/admin.ts`, `routes/subscriptions.ts` etc.) não muda — só o frontend legado é removido. Único ponto de acoplamento vivo encontrado: o botão "← Admin" no topo do Admin V2 (`AdminTopbar.tsx`), que linka de propósito pra `/admin`. Única perda funcional real identificada: o widget de status de infra (`admin-docker-status` — API/Postgres/nginx, funcional de verdade) não tem equivalente no Admin V2. O usuário decidiu explicitamente aposentar o Admin legado nesta conversa, com brainstorm de abordagem feito antes (`@project-planner`, 3 opções apresentadas) — usuário escolheu a Opção A (big bang: rota fora + branch de arquivo + remoção física, tudo num plano só), com 2 ajustes: o botão "← Admin" vira "Voltar" apontando pra SPA pública (`/`), e o widget de status Docker é portado pro Admin V2 (botão pequeno, círculo com ícone "i", não a barra completa do legado).
Decision: **Superar `DECISION-013` regras #1 e #3.** O Admin legado (`/admin`, `AdminContent.tsx`, todos os `apps/web/src/modules/admin-*` exceto `admin-docker-status` que é portado) será **removido da base local** — não fica mais coexistindo indefinidamente com o Admin V2. Regras fixadas:
1. **Admin V2 passa a ser a única superfície administrativa.** Rota `/admin` sai do roteador (`App.tsx`); nenhum redirect permanente — 404 direto (Opção A do brainstorm, não a Opção B de redirect suave).
2. **Rede de segurança:** antes de qualquer remoção física, criar uma branch de arquivo (`archive/admin-legado`, a partir do commit que ainda contém tudo) e confirmar que a base local está 100% sincronizada com `origin/main` (nada órfão só localmente) — só remover da main depois dessas 2 checagens.
3. **Backend intocado.** `apps/api/src/routes/*` não muda nesta remoção — confirmado que é 100% compartilhado com o Admin V2 (`DECISION-014` regra #2 já estabelecia isso pro que foi migrado; agora estende-se à confirmação de que nada no backend existe só pro legado).
4. **Widget de status de infra é portado, não perdido** — vira um botão pequeno (círculo com ícone "i") no shell do Admin V2, reusando a lógica de `useDockerHealth`/`DockerStatusModal` já existente, fisicamente realocado pra dentro de `admin-v2/` (não fica um módulo `admin-docker-status` órfão fora da árvore nova).
5. **Botão "← Admin" do Admin V2 vira "← Voltar"**, apontando pra `/` (SPA pública), não mais pra `/admin`.
6. **Testes E2E acoplados ao DOM do legado** (`flows.spec.ts` bloco "Admin flows", `membership-grid.spec.ts`) precisam ser reescritos contra o Admin V2 nativo ou removidos se a cobertura já existe em outro teste — não podem ficar apontando pra uma rota que não existe mais.
7. **Metas, Performance e Assinantes (tela legada) não são portados** — confirmado que os 2 primeiros nunca tiveram implementação real (nada a perder); Assinantes vira decisão em aberto separada, não bloqueia esta remoção (o app real de assinatura recorrente/cobertura de serviço nunca existiu nem no legado — ver achado do `PLAN-0032` ocorrência #6 e a conversa de revisão desta sessão).
Consequences: `DECISION-013` regra #1 ("os dois admins convivem indefinidamente") e regra #3 ("aposentadoria não decidida agora") ficam formalmente superadas por esta decisão — as demais regras da `DECISION-013` (identidade visual, arquitetura de camada `intelligence/`, Health Score v1) continuam valendas, intocadas. A execução detalhada (inventário completo, ondas, checklist) vai pro `PLAN-0033`. Qualquer proposta futura de trazer de volta uma tela do legado (ex.: se surgir necessidade real de Metas/Performance) deve nascer como funcionalidade nova no Admin V2, nunca como "restaurar o legado".
